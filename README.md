# Airship Engagement Review — Cursor Skill

A Cursor Agent Skill that turns an Airship project's **Reports API** data into a
client-ready review, output as a **self-contained interactive HTML web-app**. On screen it's
a dashboard (fixed sidebar with auto TOC + scroll-spy, fluid reading layout, per-KPI "how
it's computed" methodology, searchable tables, per-chart & per-table CSV export); the same
file prints to a paginated PDF companion when one is asked for. Default branding is Airship;
report language defaults to English (French on request).

## Two modes

| | **Mode A — Full engagement review** (default) | **Mode B — Goals review** (light) |
|---|---|---|
| Reads | The Reports API, plus the tagging plan when supplied | The tagging plan only, plus public research on the brand |
| Network | One MCP-configured client project | **None** — fully offline |
| Answers | What this account sends, to whom, with what engagement and conversion, against benchmarks | What this account should configure as an Airship **Goal** today, and which funnel stages nothing can measure |
| Delivers | `~/Downloads/<Client>_Engagement_Review_<date>.html`, plus a PDF companion on request | `~/Downloads/<Client>_Goals_Review_<date>.html` |

Mode A is the default. Mode B triggers only on an explicit ask ("goals review", "revue
goals", "quels goals configurer", "conversion review of the tagging plan"); a mode A review
that mentions goals in passing is still mode A.

**And one option orthogonal to both** — the [NotebookLM source library](.cursor/skills/airship-engagement-review/source-pack.md).
`build_source_pack.py` turns whatever a run already collected into a folder of markdown
documents to upload into Gemini Notebook Enterprise, so an account team can interrogate the
data instead of re-reading the report's conclusions. No model, no API call, no verdict: a
packager. Building it is opt-in, but **asking is not** — the pack reads the raw pulls, and
the delivery gate retires those, so the question has to be put before the first build.

## How a run flows

Three diagrams, each answering a question prose kept answering badly:

- **[The mode A wave diagram](.cursor/skills/airship-engagement-review/orchestration.md#wave-graph)**
  — collect, analyse, freeze, then write sections in parallel. Its three hexagons are the only
  places the flow goes backwards, and the cost of a backward edge grows from one script, to
  three sections, to twenty-four. That gradient is why the cheap checks come first.
- **[The mode B diagram](.cursor/skills/airship-engagement-review/mode-b.md#workflow)** — what
  is *absent* is the design: no MCP call, no collection wave, deterministic scripts end to end,
  and a single place where a model writes anything.
- **[What each check actually compares](.cursor/skills/airship-engagement-review/orchestration.md#the-pre-flight)**
  — two of the three verification steps compare two artefacts to each other, so they can only
  ever report a disagreement. Only the third judges a single artefact on its own, which makes
  it the only one that can catch an audit that is self-consistent and wrong.

## What's in the skill

The skill lives in [`.cursor/skills/airship-engagement-review/`](.cursor/skills/airship-engagement-review/).

**The method** — `SKILL.md` is the entry point and routes to the rest:

- `analysis-spec.md` — what each analysis must establish before anything is written.
- `report-structure.md` — the mode A section spine and what each section owes the reader.
- `orchestration.md` — waves, model routing, and the rules that keep a parallel run honest.
  Opens on the [wave diagram](.cursor/skills/airship-engagement-review/orchestration.md#wave-graph),
  which names all 26 canonical sections and which wave writes each.
- `mode-b.md` — the Goals review workflow, [diagrammed](.cursor/skills/airship-engagement-review/mode-b.md#workflow)
  before it is specified.
- `reference.md` — Reports API endpoints (scope `rpt` only), account shapes and collection
  strategies, definitions, branding, page rules.
- `source-pack.md` — the NotebookLM source library: when it is the right tool, what it
  emits, and who retires the raw pulls it reads.
- `setup-mcp.md` — wiring a client project as an MCP server (also summarised below).

**Reference data** — regenerated by importers, not edited by hand:

- `benchmarks.json` / `benchmarks.md` — Airship UA industry benchmarks (per vertical ×
  device family × percentile), used to position the client's KPIs vs peers.
- `event_catalog.json` / `event_catalog.md` — custom-event catalogue by vertical.
- `campaign_playbook.json` / `campaign_playbook.md` — campaign pillars, standard levers and
  vertical stakes.
- `data-collection-by-vertical.md` — data-collection best practices by vertical.

**`scripts/`** — one layer per job. Every script is runnable on its own and documents itself
with `--help`; only the collection layer touches the network.

*Collection* — the only layer that calls Airship:

- `collect.py` — the shared collector. One script for every account: it probes the account's
  shape, then routes to the collection strategy that shape can actually sustain, in parallel
  waves with per-stage deadlines and partial-result recovery.
- `push_firehose.py` — accounts too dense to enumerate push-by-push: the shape probe, the
  routing oracle, exhaustive enumeration where it's tractable, sends reconciliation where
  it isn't.
- `airship_api.py` — direct Reports-API client, for the exhaustive passes the MCP can't serve.
- `activity_log.py` — merge the activity log with `responses/list` into one push inventory.
- `channel_activity.py` — per-channel activity from `/sends`+`/devices`+`/events`: detects
  every active channel (email/SMS even at `opted_in=0`), builds the email funnel from
  standard events, classifies each channel's automated-vs-one-shot cadence.

*Brief and analysis* — no network, all offline over what collection wrote:

- `build_facts.py` — emits `facts.json`, the small shared numeric brief every section writer
  must agree with, including the `withheld` registry of metrics too thin to publish.
- `campaign_inventory.py`, `campaign_purpose.py`, `classify_campaigns.py` — the campaign
  inventory, its pillar classification, and one-shot vs automated typology.
- `event_attribution.py`, `event_analysis.py` — per-campaign attribution of conversion KPIs,
  and custom-event contextualisation.
- `decode_bodies.py` — decode the push-body caches into structured creatives.
- `parse_tagging_plan.py`, `analyze_tagging_plan.py`, `data_foundation.py` — the tagging-plan
  path, when the client supplies one.
- `resolve_vertical.py` — resolve the client's industry to a benchmark vertical, reproducibly.
- `coverage.py` — grade what a run actually managed to collect, and flag a manifest that
  claims completeness on a stage it also reports as truncated.
- `opportunity.py` — size the gap between an account and its peer median, in the direction
  that gap actually points; an account above the median gets the other sentence.
- `cross_compare.py` — two apps of one brand in one run: compare their audits and freeze
  the shared figures so both reports agree.

*Report assembly*:

- `canonical_sections.py` — single source of truth for the section spine.
- `report_framework.py` — shared assembly framework.
- `report_interactive.py` — the interactive-HTML toolkit (Flight Deck deep-links, dashboard
  scaffold, searchable-sortable-exportable tables, benchmark gauges, per-KPI methodology
  modals, interactive charts with CSV export). Pure stdlib.
- `airship_charts.py` — branded matplotlib charts **and** JSON-safe Chart.js spec emitters
  (interactive canvases share the PNGs' data).
- `build_report_template.py` — the mode A builder scaffold, copied per client.
- `sections_shared_template.py` — the `_shared.py` every section imports: the frozen numbers,
  the house formatting rules, `esc()` for anything quoted from the account, and `ref()` for
  cross-references, which resolves a canonical key to its section number rather than trusting
  a hand-typed one.
- `render_email.py`, `render_mocks.py` — render a real email / Message Center `html_body`,
  and real push previews plus illustrative mockups (Chrome headless).
- `build_report.py` — HTML → PDF (Chrome headless), with an optional page-count check.

*Mode B*: `goal_candidates.py` (the Goal qualification engine), `build_goals_template.py`,
`goals_charts.py`.

*The NotebookLM source library* — deterministic, no model in the loop:

- `build_source_pack.py` — reads `work/<client>/` and emits the pack, with its own gate.
- `source_pack_corpus.py` — routes the skill's own reference material into the pack's
  tier-1 documents, and reports any heading it routed nowhere.
- `source_pack_docs.py` — renders the account's data as markdown a notebook can read.
- `report_markdown.py` — the delivered report as a markdown source.
- `merge_source_packs.py` — one pack across several apps of the same brand.

*Gate and tests*:

- `verify_audit.py` — the pre-flight: asks whether `audit.json` is *plausible*, before charts
  and sections are built on it. The only check with a single input, and so the only one that
  catches an audit that is wrong but self-consistent.
- `verify_report.py` — the delivery gate: a report that fails it is not delivered.
- `run_selftests.py` — every offline self-test in the directory. No credentials, no network,
  no project. Run it after touching any script.
- `probe_sweep.py` — the routing acceptance test: run the shape probe across many projects
  at once and compare against a local `probe_sweep_expected.json` (copy the shipped
  `.example.json`; the real one names accounts and stays git-ignored).
- `check_section.py` — check one section file against the gate's rules before the whole
  report is built, so a wave-4 agent finds its own mistakes.
- `check_brand.py` — validate `brand.json` against `brand_schema.json`: the flat shape
  `goal_candidates.resolve_context()` reads, the field caps the layout imposes, and the
  source budget wave 0 is held to.
- `check_no_client_names.py` — fails if an account name reaches a tracked file.
- `import_benchmarks.py`, `import_event_catalog.py` — regenerate the reference data above
  from their source workbooks (once per new quarter).

## Install in Cursor

Skills are discovered automatically from `.cursor/skills/` (project) or
`~/.cursor/skills/` (global). There is no separate Skills settings page — installed
skills appear under **Cursor Settings → Rules → Agent Decides**.

### Option A — Open this repo as your workspace (recommended)

Best for running reviews from a dedicated project. No extra install step.

1. In Cursor, open the Command Palette (`Cmd+Shift+P` / `Ctrl+Shift+P`).
2. Run **Git: Clone** and paste:
   ```
   https://github.com/thomasfaro/client-activity-pdf
   ```
3. When prompted, **Open** the cloned folder in Cursor.
4. Verify the skill loaded: **Cursor Settings** (`Cmd+Shift+J` / `Ctrl+Shift+J`) →
   **Rules** → look for `airship-engagement-review` under **Agent Decides**.
5. In Agent chat, ask e.g. *"generate an Airship engagement review for user-XX PROD"*.

The skill auto-loads because this repo already contains `.cursor/skills/airship-engagement-review/`.

### Option B — Use the skill in any existing project (global install)

Keeps the skill available across all your workspaces.

1. Clone this repo anywhere on your machine (Command Palette → **Git: Clone**, or
   Cursor's integrated terminal):
   ```bash
   git clone https://github.com/thomasfaro/client-activity-pdf.git
   cd client-activity-pdf
   ```
2. Run the install script from Cursor's terminal (`Terminal → New Terminal`):
   ```bash
   ./install.sh            # symlink → ~/.cursor/skills/ (live updates on git pull)
   ./install.sh --copy     # copy instead of symlink
   ```
3. Reload Cursor: Command Palette → **Developer: Reload Window**.
4. Verify: **Cursor Settings → Rules → Agent Decides** → `airship-engagement-review`.
5. Open any project and ask the Agent to run a review (you still need the target
   project's Airship MCP server configured locally).

To remove: `./install.sh --uninstall`

### Option C — Add to a specific project only

If you want the skill inside one client repo without a global install:

1. Clone this repo (or add it as a submodule).
2. Copy the skill folder into your project's `.cursor/skills/`:
   ```bash
   mkdir -p .cursor/skills
   cp -R /path/to/client-activity-pdf/.cursor/skills/airship-engagement-review .cursor/skills/
   ```
3. Reload Cursor (**Developer: Reload Window**).
4. Commit `.cursor/skills/airship-engagement-review/` if you want teammates to get it
   when they open that project.

### GitHub import via Settings (experimental)

Cursor documents a GitHub import under **Cursor Settings → Rules → Project Rules →
Add Rule → Remote Rule (GitHub)**. Paste the repo URL:

```
https://github.com/thomasfaro/client-activity-pdf
```

This flow is designed for `.mdc` rules; skill-only repos may not always register
under **Agent Decides**. If the skill does not appear after a reload, use Option A, B,
or C instead.

## Use it

Once installed, invoke the skill from Agent chat:

- Ask naturally: *"generate an Airship engagement review for user-XX PROD"*
- Or reference it with `@airship-engagement-review` (if shown in the `@` menu)
- Or type `/airship-engagement-review` in the chat input

**Launch it as a Custom Mode** (Option+Enter on Mac, Alt+Enter on Windows) rather than a
plain chat. A full review is long enough that a normal chat can compact away the collected
data mid-run, and the first symptom is a thin section written from memory.

For **mode A**, the Agent pulls data from the project's Airship MCP server, generates charts
and creatives, runs the delivery gate, and writes
`~/Downloads/<Client>_Engagement_Review_<date>.html` (macOS *Téléchargements*). The HTML is
the deliverable; ask for the PDF companion if you want one, and it is built alongside.

For **mode B**, ask explicitly — *"goals review for user-XX from this tagging plan"* — and
hand over the `.json`. No MCP server needed: the whole review is produced offline and lands
as `~/Downloads/<Client>_Goals_Review_<date>.html`.

## The client's tagging plan — optional for mode A, required for mode B

A mode A review is complete without it, and **mode B cannot run at all without it** — the
Goals review reads nothing else. When you supply the client's **RTDS data collection
audit** export (`.json`), mode A adds a *Data foundation & tracking coverage* section and
turns several conversion verdicts into facts: which KPIs are backed by `value`/currency, which
conversion events are tracked but never fired, and the real taxonomy of events, attributes,
tags and subscription lists. Parsing and analysis are already vendored in the skill — you only
have to hand over the file.

Ask the client for their export, or produce one yourself with the companion app — no terminal
needed:

1. Get [airship-rtds-data-collection-audit](https://github.com/thomasfaro/airship-rtds-data-collection-audit)
   (private repo — ask for access) and follow its `docs/INSTALL.md`: clone it with GitHub
   Desktop, then double-click `Start RTDS Data Collection Audit.command` on macOS or the `.bat`
   on Windows. It installs whatever is missing, Node.js included.
2. Add the project's RTDS bearer token under **Projects**, then start a capture from
   **Capture**. Real-time auto-stop ends it on its own; for a project fed by batch API calls,
   use manual stop and keep it running across a full batch cycle or the plan will miss whatever
   the batches carried.
3. On the coverage summary, click **Download .json**.

Then point the Agent at that file when you ask for the review.

## Configure client projects as MCP servers in Cursor

Needed for mode A only; mode B runs offline. The steps below are the short version of
[`setup-mcp.md`](.cursor/skills/airship-engagement-review/setup-mcp.md), which the Agent
reads when a project turns out not to be wired yet.

The skill does **not** embed Airship credentials. Each client Airship project must be
wired as a separate MCP server on your machine.

### Step 1 — OAuth in the Airship dashboard (once per project)

1. Open the client's project in Airship Go.
2. **Settings → Project settings → OAuth** → create or edit a client.
3. Enable **Allow Basic Auth** (required for Client Secret).
4. Enable scope — **only `rpt` (Reports)** — required for sends, opens, devices, events,
   activity log, perpush/pergroup, etc.
   Do **not** require `tpl` (Content) — this skill never calls `/api/content/*`.
   Do **not** rely on `pln` / `sch` / experiment management scopes — this skill uses only
   Reports endpoints (plus Reports experiment *report* URLs when A/B is detected).
5. Copy **App Key** (Settings → General), **Client ID**, and **Client Secret**.
6. Note the region: **`eu`** or **`us`**.

### Step 2 — Airship MCP runtime

Install the Airship MCP server (`airship-mcp` from the agent-tools package). You need
[`uv`](https://docs.astral.sh/uv/) on your PATH and a local clone of the agent-tools
repo (path used in the config below).

### Step 3 — Cursor MCP config

**Cursor Settings → MCP** (or edit `~/.cursor/mcp.json`). Add **one entry per client**:

```json
{
  "mcpServers": {
    "Client A PROD": {
      "command": "uv",
      "args": ["run", "--directory", "/path/to/agent-tools", "airship-mcp"],
      "env": {
        "AIRSHIP_APP_KEY": "<app_key>",
        "AIRSHIP_CLIENT_ID": "<oauth_client_id>",
        "AIRSHIP_CLIENT_SECRET": "<oauth_client_secret>",
        "AIRSHIP_REGION": "eu"
      }
    }
  }
}
```

Replace `/path/to/agent-tools` with your local install path. Duplicate the block for
each client (`Client B PROD`, `Client C PROD`, …) with that project's credentials.

Reload Cursor (**Developer: Reload Window**) or restart the MCP row in Settings.

When you ask the Agent for a review, name the server as configured (e.g.
*"engagement review for **Client A PROD**"*). Internally Cursor addresses it as
`user-Client A PROD`.

### Step 4 — Smoke test

Ask the Agent to call `GET /api/reports/devices` on that MCP server. Expect HTTP 200
with platform opt-in counts. If you see **401 Expired token**, restart the MCP server.
If **401 Missing required scope**, add the scope in Airship OAuth settings and restart
the MCP server.

**Security:** keep `mcp.json` local; never commit credentials to git.

## Client data, provenance and review

A run pulls a client's real send history into `work/<client>/` and produces a document whose
commentary a model drafted. **The report is an internal Airship document**: it prepares the
account team for a conversation with the client rather than being sent to them. The exposure
is therefore indirect — a figure repeated in a meeting travels just as far as a page would —
and four rules cover it, enforced rather than left to memory.

The report carries a **provenance footer** naming the data source and the model that actually
wrote the prose, read from `work/<client>/run.md`, and **every page is marked internal use**
(including, via a print-only running footer, every sheet of the PDF). The gate blocks a report
missing either. A `Reviewed-by: <name>` line in that same `run.md` is quoted by the footer
when present, but is not required to deliver.

Finally, **raw pulls do not outlive the run that needed them**. A successful, delivered build
drops `work/<client>/data/` on its way out; the 30-day window below is the net for runs that
never finished:

```bash
python scripts/purge_work.py            # report what is past the window
python scripts/purge_work.py --apply    # drop the raw pulls, keep what rebuilds the report
python work/<client>/build_report.py --keep-raw   # keep data/ while investigating
```

What survives is what a rebuild opens — the numbers, the layout, the rendered charts and
creatives — so a report can be rebuilt in the other language or after a framework fix without
calling the API again. `work/` is git-ignored, so none of this data has ever been committed.

## Working on the skill itself

Three checks, all about the skill rather than any client report.

```bash
cd .cursor/skills/airship-engagement-review
python scripts/run_selftests.py
```

Offline, no credentials, a few seconds. It exercises the pure functions that decide what
reports say — the contamination detector, the detail-ranking cap, the routing oracle, the
`audit.json` → `facts.json` coherence check — plus the provenance footer, the retention rule
and the redaction of personal sample values out of a tagging plan, and exits non-zero on the
first broken assertion. Run it after touching any script.

```bash
python scripts/check_no_client_names.py
```

The repository ships benchmarks and general practice, never a client. This reads the account
list out of `~/.cursor/mcp.json` — where every reachable project is declared as
`<project> <ENV>`, outside the repository by construction — and fails if one of those names
appears in a tracked file. **The check is shipped, the names are not**, so a fresh clone gets
the guard and no portfolio. Run it before committing; on a machine pointed at no project it
says so and exits 0. Names of two or three characters, and names that are ordinary English
words, are searched only beside `PROD`/`DEV` or `user-`, and the output lists which ones.

It covers the **whole repository** wherever you run it from, and prints the root it resolved
so you can see that. That is worth stating because it was not always true: the root used to
default to the working directory, `git ls-files` inside a subdirectory lists only what is
under it, and run as documented above the guard read 81 of 94 tracked files — missing
a `docs/` tree and this README, which is how a client name reached a compliance document
with the check reporting `ok`.

```bash
python scripts/probe_sweep.py --expect scripts/probe_sweep_expected.json
```

The routing acceptance test: probes many configured projects and compares each account's
detected shape against the recorded ground truth. This one **does** call the API (a few
hundred calls) and needs the MCP servers configured, so run it when you change routing, not
on every edit.

Both of its files are git-ignored, and for the same reason: `probe_sweep.json` records real
volumes per named account, and the expectation file pairs each account with its regime,
which is a commercial fact about it. Copy `scripts/probe_sweep_expected.example.json`, which
ships placeholder names, and fill in the projects on your machine.

## Requirements

- Python: `matplotlib`, `numpy`, `pillow`, `openpyxl` (benchmark import); `pymupdf`
  optional (only for the PDF page-count sanity check). `report_interactive.py` is pure stdlib,
  and `run_selftests.py` needs nothing beyond the standard library.
- Google Chrome (headless) for HTML→PDF, email and mockup rendering
- [`uv`](https://docs.astral.sh/uv/) + Airship MCP (`airship-mcp` / agent-tools)
- One Cursor MCP entry per client project (see above)
- Optional: the [RTDS Data Collection Audit app](https://github.com/thomasfaro/airship-rtds-data-collection-audit)
  when you want to feed a tagging plan into the review (see *Optional input* above)

## Sharing

Clone and follow one of the install options above; pull to get updates. For team-wide use
inside a client project, prefer **Option C** (commit the skill folder into that repo's
`.cursor/skills/`).

The skill is public, and what it runs on is not. It ships benchmarks, vertical reference
data and general practice; it carries no credentials, no account list and no client data.
Running it against an Airship project means wiring **your own** project as an MCP server
with **your own** OAuth credentials, which live in `~/.cursor/mcp.json` and never enter the
repository. `check_no_client_names.py` is the guard that keeps it that way, and it runs
against the whole tree.
